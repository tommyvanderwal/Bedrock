# Bedrock codebase rewrite plan

**Status**: plan for the post-0.8-alpha cleanup. Do NOT execute mid-feature;
draft now so we know what we're aiming at while 0.8-alpha hardens.

**Why a rewrite at all** — 0.8 alpha already works end-to-end on the
testbed (when init/join/leave succeed). The pain isn't *functional*;
it's that the code path is hard to follow when something breaks. A
fresh engineer (or future-self at 3 a.m.) opening the repo to debug
an e2e failure can't easily answer: *what step is bedrock init on
right now, what state did it leave behind if it crashed there, and
which module owns that step?* The rewrite is about making that
question one-grep-away.

This document supersedes the earlier file-size-reduction plan.

---

## 1. Goals (in priority order)

1. **One linear, traceable code path per operation.** `bedrock init`,
   `bedrock join`, `bedrock node leave`, `bedrock vm create`, etc. —
   each should map to ONE handler that submits ONE saga; the saga's
   step list IS the operation's flow chart. No more reading 4 modules
   to figure out what runs in what order.
2. **Single source of truth for cluster state.** rqlite is
   authoritative. Anything else (`state.json`, `cluster.json`,
   per-node files) is either bootstrap-only or a derived
   snapshot. No module writes to both rqlite AND a sidecar file
   for the same fact.
3. **Crash-safe everything.** Every multi-step operation is a saga
   in rqlite (`operations` + `operation_steps`). Power-loss at any
   step → resume from the last completed step on next boot.
4. **One Bedrock-owned daemon.** `bedrock-d` is the only Bedrock
   systemd unit. It starts/stops rqlited, weed-*, drbd, libvirtd
   per saga steps. No service dependency cycles (current pain
   point: `bedrock-d Requires=bedrock-rqlited` and rqlited needs
   the env file that bedrock-d's init writes → deadlock at first
   boot).
5. **CLI is a thin HTTP client.** `bedrock <cmd>` submits a saga,
   tails its log via WebSocket, polls for completion. No direct
   imports of `installer.lib.*` from the CLI. The CLI binary
   stays under 200 lines.
6. **Domain-grouped modules, not layer-grouped.** Keep `vm/create`,
   `vm/migrate`, `storage/drbd`, `storage/seaweed`, `net/mesh`,
   `net/witness` together by what-they-do. No `routes/`,
   `services/`, `repos/` Java layers.

## 2. The current pain (concrete observations)

Drawn from the live 0.8-alpha codebase + the e2e failure that
prompted this plan.

### 2.1 Module sprawl

- `installer/lib/` has 30+ `.py` modules. Many cohere (witness.py,
  election.py, cluster_arbiter.py) but the relationships are
  ad-hoc: `tier_storage.py` imports `bedrock_state`, `cluster_addr`,
  `daemon_setup`, and writes both to rqlite AND to per-node JSON
  files for the same facts.
- `mgmt/app.py` is 5,411 lines and ~9 distinct domains.
- `installer/iso-build/{payload,build}/lib/*.py` are STAGED COPIES
  of `installer/lib/*.py`. Easy to drift.

### 2.2 State split across three places

- `state.json` — per-node bootstrap (cluster_uuid, node_name,
  loopback_ip, cluster_key path). Written once on install.
- `cluster.json` — per-node cached cluster view (nodes, vms,
  tiers, witnesses, ...). Generated by mgmt fold; some code reads
  it directly, some recomputes from rqlite, some writes to BOTH.
- rqlite — authoritative.

The friction: it's not always clear which source the calling code
trusts. When facts drift, the bug surfaces minutes later in a
seemingly unrelated component.

### 2.3 Procedural init/join with no resume

`bedrock init` is a procedural shell-style sequence:
1. `os_setup` (sysctl, firewall off, NTP)
2. `tier_storage.setup_n1()` (provision local LV tiers)
3. `rqlite_setup` (write env, start rqlited, wait for Leader)
4. `bedrock_state.seed_schema()`
5. write cluster.json, state.json
6. `seaweedfs.write_env_file` + `promote_to_master_volume_host`
7. start bedrock-d

If step 4 crashes, there's no record of where we were. Re-running
`bedrock init` may or may not work; some steps are idempotent, some
aren't. The recent e2e failure showed this concretely:
`tier_storage.setup_n1()` tried to write to rqlite BEFORE step 3
started rqlite — multiple `tier_state write skipped: ConnectError`
warnings — and then rqlited never reached Leader, so the cluster
ended up half-initialised with no resume path. The whole `bedrock
init` returned "success" because the failures were warnings, not
errors.

### 2.4 Service dependency cycles

- `bedrock-d.service` `Requires=bedrock-net.service`
- `bedrock-rqlited.service` `EnvironmentFile=/etc/bedrock/rqlited.env`
- `rqlited.env` is written by code that runs INSIDE `bedrock-d`
  during init
- If bedrock-d crashes mid-init, rqlited can never start because
  its env is missing. If rqlited can never start, bedrock-d's
  rqlite-subscriber blocks. Deadlock.

The fix is "install.sh doesn't enable bedrock-rqlited; bedrock-d
enables it at the right step". Today this is half-true; the rewrite
makes it fully true.

### 2.5 CLI does too much

`bedrock <subcmd>` directly imports `installer.lib.tier_storage`,
runs operations IN the CLI process, writes to /etc/bedrock/*.json,
and shells out to systemd. Errors mid-flow leave inconsistent state
and the CLI exit code doesn't reflect partial-success accurately.

### 2.6 Tests check outcomes, not invariants

`test_e2e_offline.sh` asserts "cluster size == N", "S3 marker round-
trips", "arbiter active on master" — outcomes. When an outcome
fails, the test gives a number but no breadcrumb into WHY. No
in-process unit tests for the pure functions (election.compute,
saga-step idempotency) means refactors rely entirely on the 20-min
e2e for safety.

## 3. Target shape

### 3.1 One process, three concerns

```
bedrock-d (single Python process per node)
├── netd thread           ← critical / 1 Hz / deterministic
│   ├── mesh probes + path table
│   ├── election (weighted vote, NoQuorum self-demote)
│   ├── witness IO (set_own_slot, drain_replies)
│   └── route emission (per-peer /32 + transit + panic catch-all)
│
├── orchestrator task     ← calm / 10-30 s / deliberate
│   ├── rqlite revision watcher
│   ├── saga executor (operations + operation_steps)
│   ├── service reconciler (start/stop rqlite, weed-*, drbd, libvirt)
│   └── membership rebalancer (cluster-DRBD set, weed-master Raft-3,
│                              SeaweedFS replica fix-up)
│
└── mgmt FastAPI app      ← operator surface
    ├── /api/operations   ← submit + poll sagas
    ├── /api/cluster      ← read derived view
    ├── /ws               ← live state + saga progress stream
    └── /isos, /vms, ...
```

The three concerns share **one** state object (`BedrockState`),
locked where needed. Inter-concern signalling is through rqlite
revisions, not direct calls.

### 3.2 Saga-driven everything

Every operation that touches more than one local command is a saga:

```python
@saga("vm_create")
class VmCreate:
    target: "self" | "master" | "auto"

    @step("lvcreate_data")
    def step_data_lv(self, params): ...   # idempotent

    @step("lvcreate_meta")
    def step_meta_lv(self, params): ...

    @step("drbd_create_md")
    def step_create_md(self, params): ...

    @step("drbd_bring_up")
    def step_drbd_up(self, params): ...

    @step("libvirt_define")
    def step_libvirt(self, params): ...
```

The executor:

1. Loads the saga class by `kind`.
2. Iterates steps in declared order.
3. For each step: if `operation_steps(op_id, step_name)` already
   has `state='done'`, skip. Otherwise call the step method; on
   success, write `state='done'`; on exception, write
   `state='failed'`+error and bubble up.
4. On final success, update `operations.state='completed'`.
5. On startup: query `operations WHERE state IN ('pending','in_progress')
   AND target_node = self`, resume from first not-`done` step.

Every step is idempotent. Every step's "did this already happen?"
check is the step's first 3 lines — either skip or do.

### 3.3 State sources

- **rqlite** — authoritative for: cluster membership, mgmt_master,
  tier state, vm desired state, drbd_resources, sagas, S3 IAM,
  backup targets, witnesses.
- **state.json** — bootstrap-only: cluster_uuid, cluster_key path,
  node_name, loopback_ip, role. Written once at install; read on
  every bedrock-d startup to prime the in-process state.
  Never written-to by sagas.
- **cluster.json** — derived snapshot. Regenerated from rqlite by
  the orchestrator every revision change. Only READ by other
  modules (and bedrock CLI for offline operator queries when
  bedrock-d is down). Never written by anything except the
  snapshot task.

Strict rule: ONE module owns rqlite I/O (`bedrock_d/state.py`).
Every other module calls it. Mocking the state module is the
unit-test seam.

### 3.4 CLI as thin client

```
$ bedrock init --name foo
  → POST localhost:8443/api/operations  {kind: "cluster_init", params: {...}}
  → tail WS /api/operations/123/log
  → poll /api/operations/123 until state in ('completed','failed')
  → exit 0 or print error
```

The CLI is a stand-alone Python script under 200 lines:
- subcommand parsing
- HTTP client to bedrock-d
- WebSocket consumer for live step output
- exit code reflects final saga state

The CLI never imports `bedrock_d.*` modules. Operator can use the
CLI from a different node if they want — it's just an HTTP client.

### 3.5 Service-unit simplification

- **bedrock-d.service** — the ONLY Bedrock systemd unit installed
  as `WantedBy=multi-user.target`.
- **bedrock-rqlited.service** — installed, `WantedBy=` empty.
  bedrock-d starts it via a saga step (init writes the env, then
  systemd-enables + starts).
- **bedrock-rqlited-arbiter.service** — same pattern, started by
  the arbiter-promote saga step.
- **bedrock-weed-{master,volume,filer,s3}.service** — installed,
  `WantedBy=` empty. bedrock-d's calm orchestrator enables the
  right ones per the `seaweed_master_membership` table and the
  arbiter role.
- **drbd, libvirtd** — `systemctl disable` at install. bedrock-d
  starts them when there's actual work to do.

No service-level dependencies cross Bedrock units. Order is
controlled by saga step ordering. systemd manages bedrock-d only.

## 6. Hard rules during the rewrite

1. **No stage skips the e2e green-bar.** A stage that breaks e2e
   is reverted, not papered over.
2. **No stage changes more than one concern.** Don't merge "split
   app.py" with "introduce sagas" — each is its own PR.
3. **No new files until they have a home.** New module → add to
   the directory tree in this doc first, then write the file.
4. **No `utils.py` anywhere.** Helpers live next to their callers
   or get a properly-named module.
5. **No `if version_X` branches.** This is a single-version
   codebase. The previous code is in git history.
6. **No type-driven over-abstraction.** No ABCs/Protocols unless we
   have two real implementations in flight.
7. **One rqlite-writing module.** `bedrock_d.state` is the only
   place that POSTs to rqlite. Everything else calls it.

---

## 7. Out of scope for this rewrite

- Adding new features. The rewrite is purely structural.
- Switching languages (no Rust reintroduction, no Go).
- Replacing rqlite / SeaweedFS / DRBD / libvirt. These are stable
  and well-understood; the rewrite is about how Bedrock USES them.
- Multi-datacenter, multi-witness quorum, erasure-coded SeaweedFS.
  Post-rewrite features.
- Web dashboard rework. The mgmt routes change shape; the Svelte
  UI keeps consuming `/api/cluster` + `/ws` and is unaffected.

---

## 8. Open questions to answer before stage 0

- **Saga log persistence**: do we keep completed sagas indefinitely
  in rqlite, or vacuum after 30 days? Recommendation: keep last
  1000 per node + last 30 days, whichever bigger.
- **Saga step granularity**: how small is "one step"? Rule of
  thumb: each step ≤ 10 s wall-clock, each step idempotent
  in isolation, each step has a 1-line check that says "already
  done? skip".
- **Concurrent sagas**: can two sagas run on the same target node
  simultaneously? v0.8-alpha-on-rewrite: no — orchestrator runs
  them serially per node. Concurrency is a v0.9 concern.
- **CLI fallback**: when bedrock-d is down, what happens to
  `bedrock` commands? Recommendation: a `--local` flag for
  emergency diagnostics that reads `cluster.json` + state.json
  directly. Read-only.

## 10. The e2e failure that motivated this plan (RCA snippet)

For the record — the breakage on the rerun of `test_e2e_offline.sh`
after the SeaweedFS-config + path-migration changes:

```
Step 0 "Confirm all 4 sims have firstboot-done"  →  PASS (4/4)
Step 1 "bedrock init on sim-1 → N=1"
  output:
    [state] tier_state write skipped: rqlite POST gave up after
            4 attempts. Last error: ConnectError('[Errno 111]
            Connection refused')        ← tier_storage trying to
                                          write to rqlite BEFORE
                                          rqlite is up
    [tier] bulk        30G  -> /var/lib/bedrock/local/bulk
    [state] tier_state write skipped: ConnectError ...
    [tier] critical     5G  -> /var/lib/bedrock/local/critical
    [tier] N=1 setup complete
    WARN: rqlited didn't reach Leader within 30s
    WARN: rqlite seed failed: ConnectError ...
    Cluster test-fresh initialised.
    Dashboard: http://192.168.2.37:8080
  ← exits 0 despite the WARNs
  assertion: cluster size @ sim-1 = 1
  bedrock node-list returned empty / non-JSON  →  Traceback
```

Three smells visible in one failure:
- **state-write before service-up** (tier_storage doesn't wait for
  rqlite to be Leader before its first write)
- **warning, not error** (init "succeeds" with rqlite half-up)
- **no resume**: re-running init would face an even messier state
  because some files were written, some weren't

The saga rewrite makes this concrete failure impossible:
`cluster_init` saga step order would be `rqlite_start →
rqlite_seed_schema → tier_local_setup`, each step idempotent and
fail-loud. A failure at step `rqlite_seed_schema` leaves a clear
`operation_steps` row; the executor on next bedrock-d start
resumes from there.

This RCA also flags an **immediate fix** to land before the
rewrite begins, so 0.8-alpha can be testable while the rewrite is
in flight:

- `tier_storage.setup_n1()` must not call `bs.write_*` until after
  rqlite is confirmed-Leader.
- `bedrock init` should exit non-zero on any "WARN: rqlite ..."
  during the seed phase.
- `bedrock-d.service` should NOT have `Requires=bedrock-rqlited` —
  bedrock-d starts rqlite itself when ready.

These are point fixes; the rewrite is the structural answer.
